# Mandelbrot Performance Audit

Date: 2026-10-04. This is a local diagnostic measurement, not a general language
benchmark or a completed optimization milestone. No playground source or user
output was modified.

## Workload And Method

- Intel Core i7-13620H, Windows 11 (build 26100).
- 800 x 800 pixels, at most 100 iterations per pixel, `f64`/double arithmetic,
  the coordinate mapping and RGB palette from the user playground.
- Sequential execution, no vectorized Python libraries, no fast-math.
- ASCII PPM P3, LF line endings, 5,156,528 output bytes.
- Hand-written C++ uses a reserved string and `std::to_chars`; C# uses
  `StringBuilder`; Python uses formatted lines and `join`. These are equivalent
  workloads using idiomatic efficient output construction, not identical storage
  implementations. Their compute and formatting passes are separate; the Wio
  playground interleaves them.
- GCC/MinGW 15.2.0, C++20, `-ffp-contract=off`, `-O0` and `-O2`; C# .NET 9
  Release (SDK 9.0.311, runtime 9.0.13); CPython 3.12.14.
- Wio generated by `build/app/Debug/wio.exe` at compiler revision `2aaac3e`,
  importing the installed std. Installed and repository `builders.wio` have
  identical SHA-256 hashes. Generated code is compiled against repository
  runtime/SDK headers and `build/runtime/backend/libwio_runtime.a` with GCC
  `-O0`/`-O2`, `-static`, and `-Wa,-mbig-obj`. The runtime library is not rebuilt
  as an optimized Release library for this experiment.
- Compilation is excluded from execution times. External wall time includes
  process startup, program execution, file write/close, and exit, but excludes
  hash validation. File writes use the normal OS cache, not a durable disk sync.
- C++/C#/Python each run three times; report medians. Wio runs separately, once
  per configuration, with a 300-second per-run diagnostic timeout. These are
  preliminary measurements, not statistically qualified performance budgets.

Local diagnostic fixtures and outputs are in `build/mandelbrot-audit`, an ignored
build directory. `measure.ps1` runs each process sequentially in its own output
directory and validates completed PPM files with SHA-256. The user playground
output is read only for validation.

Each column is its own median; rounded columns need not sum exactly. All
baseline runs execute 11,613,930 Mandelbrot iteration steps. All twelve generated
files, and the existing user playground file, have SHA-256:

```text
1984A4F3A3575BD438EBD79F6EC3D0EB571BD141E5A9CBD29DFABA37941FF733
```

Neither Wio process completed within 300 seconds; each was terminated at its
own timeout. Neither produced an output file, so these fresh Wio runs have no
output hash or separate computation/formatting timing. Do not turn the timeout
into an exact duration. Validation of the existing user output establishes
image equivalence for the reference workload, not completion of these fresh
runs. Adding `-O2` to this generated code is insufficient to make this workload
practical; the representation/algorithm costs need to change.

## Confirmed Representation Costs

The generated C++ file is 2,664,592 bytes and 53,278 lines for this workload.
This includes the imported/built-in surface; it is not the size of just the
Mandelbrot loop. Capability-driven pruning and backend build scalability remain
important separate work.

The generated `StringBuilder.AppendLine` constructs a new string from the
entire previous buffer plus the new line, then replaces the old buffer. Thus
the growing prefix is repeatedly copied rather than appending into retained
capacity. With roughly fixed-size pixel lines, accumulated copying grows
quadratically in the number of pixels. This representation defect is confirmed;
the exact share of total Wio runtime versus numeric/place/call overhead still
requires separate profiling. Debug/Release flag policy alone cannot repair this
algorithmic cost.

## Binary Image Output Support

Wio already provides `byte`/`u8` arrays, `std::buffer::ByteBuffer`, `BytePool`,
`std::builders::ByteWriter`, and `std::io::OpenWriteBinaryFile`/`WriteBytes`.
`ByteBuffer.ToArray` clones its storage, so this is not a zero-copy finalization
API. These surfaces exist; their presence does not establish optimized end-to-end
throughput.

PPM P3 is valid textual output. PPM P6 instead stores RGB channels as bytes:
800 x 800 x 3 = 1,920,000 payload bytes plus a small ASCII header. This removes
per-channel decimal formatting and shrinks this image's output. It does not
change the Mandelbrot arithmetic. A P6 benchmark must be compared with P6
implementations, not substituted into the P3 timing table.
